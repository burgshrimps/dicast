# tests/data/callers — real SV-caller output, one file per caller/dialect

Real (not synthetic) raw output from the SV callers dicast is meant to accept:
delly, manta, lumpy/svtyper, smoove, gridss, cnvnator and dysgu. Each file
exercises a genuinely different VCF dialect (contig naming, ID scheme,
SVTYPE/END/SVLEN encoding, sample-column count, sequence-resolved vs.
symbolic ALTs) so `dicast/vcf_input.py`'s normalizer is proven against real
caller quirks, not just synthetic fixtures. Every file is bgzip+tabix'd and
kept to <=100 records. See `tests/unit/test_vcf_input_real.py` for the
per-file expected kept/dropped counts (hand-derived independently of the
parser) and `tests/unit/test_dicast.py` for the multi-caller end-to-end test
that runs `dicast call` across all of the hg38 chr21 files at once.

11 files are downloaded byte-for-byte from public GitHub example/benchmark
repos (trimmed only when the source had more than 100 records); the other 8
have no public raw-output equivalent (delly/manta/lumpy/smoove/cnvnator/
dysgu run against a real HG002 BAM slice, plus a gridss run and its
SIMPLE_TYPE-annotated companion) and were generated by running each caller
against a real chr21 slice of the public GIAB HG002 300x Illumina BAM on a
lab compute node (`gameboycolor.molgen.mpg.de`). Both groups' regeneration
recipes are below.

worktree/environment — the plan's `bcftools view | head` recipe does not
apply here. `bgzip`/`tabix` came from
`/Users/burgshrimps/.local/share/mamba/envs/dicast-verify/bin/{bgzip,tabix}`;
all record-count/stat verification used pysam 0.24 from that same env, not

## gameboycolor runs — real caller output on an HG002 chr21 slice

No public raw output exists for delly/manta/smoove/lumpy/cnvnator/dysgu run
on hg38 chr21, nor for a gridss run with `simple-event-annotation.R` applied,
so these 8 files were produced by actually running each caller. All work
happened under `~/dicast_callers` on `gameboycolor.molgen.mpg.de` (32 cores,
251 GB RAM, internet access, no conda/docker preinstalled — micromamba was
bootstrapped there first), with each caller in its own bioconda env to avoid
dependency conflicts.

### 1. Reference: hg38 chr21 only

```bash
source ~/dicast_callers/env.sh   # sets MAMBA_ROOT_PREFIX / PATH for micromamba
mkdir -p ~/dicast_callers/ref
# UCSC hg38 chr21.fa (chr21-only FASTA)
samtools faidx chr21.fa                       # index for every caller
bwa index chr21.fa                             # gridss needs a bwa index
# cnvnator wants one FASTA per chromosome in its own directory:
mkdir -p ~/dicast_callers/ref/chroms && cp chr21.fa ~/dicast_callers/ref/chroms/
```

### 2. Caller BAM: a real ~30x HG002 chr21 slice, never committed

Streamed (not fully downloaded) from the public GIAB AshkenazimTrio HG002
GRCh38 300x novoalign BAM (same source as `tests/data/demo.bam`, see
`tests/data/README.md`):

```
https://ftp-trace.ncbi.nlm.nih.gov/ReferenceSamples/giab/data/AshkenazimTrio/HG002_NA24385_son/NIST_HiSeq_HG002_Homogeneity-10953946/NHGRI_Illumina300X_AJtrio_novoalign_bams/HG002.GRCh38.300x.bam
```

Region: the 20 `tests/data/demo_delly.vcf.gz` loci padded +/-5kb, plus one
contiguous 5 Mb window (chr21:20-25 Mb) for read-pair/split-read signal away
from the demo loci, downsampled to ~30x (`samtools view -s`), reheadered to
a chr21-only header, mates on other contigs dropped, sorted and indexed:

```bash
samtools view -b -o slice_full.bam "$BAMURL" chr21:REGION1 chr21:REGION2 ... chr21:20000000-25000000
samtools view -b -s 42.3 -o slice_ds.bam slice_full.bam     # ~30x
samtools reheader chr21_only_header.sam slice_ds.bam > slice_rh.bam
samtools view -h -e 'rnext=="chr21" || rnext=="=" || !(flag & 1)' -b -o ~/dicast_callers/bam/caller.bam slice_rh.bam
samtools sort -o ~/dicast_callers/bam/caller.bam ~/dicast_callers/bam/caller.bam
samtools index ~/dicast_callers/bam/caller.bam
```

`~/dicast_callers/bam/caller.bam` (built by a separate remote-setup step, via
a textual `samtools view` reheader) has **no `@RG` line**; smoove/lumpyexpress
need one (see "Problems encountered" #2), so a separate `caller_rg.bam` copy
with an added `@RG` was created for those two callers rather than mutating
the shared BAM other callers also read.

### 3. Per-caller env + run

```bash

REF=~/dicast_callers/ref/chr21.fa
```

**delly** (`delly_hg38_chr21_hg002.vcf.gz`, 27 records: DEL=15, INS=11, DUP=1):
```bash

# fails with "Unrecognized command call". `sr` takes the same -g/-o/BAM args,
```

**manta** (`manta_hg38_chr21_hg002.vcf.gz`, 28 records from `diploidSV.vcf.gz`;

**cnvnator** (`cnvnator_hg38_chr21_hg002.vcf.gz`, 38 records: DEL=21, DUP=17):

### 4. Fetch + trim locally

Every remote raw VCF was `scp`'d back and processed with pysam (the
`dicast-verify` env), never bcftools:

```bash
scp gameboycolor.molgen.mpg.de:~/dicast_callers/out/<caller>/<file>.vcf <scratch>/
```

All 8 raw outputs except the two gridss/candidateSV ones were already
<=100 records and needed no trimming — just
`pysam.tabix_compress`(bgzip)/`pysam.tabix_index(preset='vcf')`(tabix)
straight into `tests/data/callers/`. `gridss_raw.vcf`/`gridss_simple.vcf`
(912 records each) and `candidateSV.vcf.gz` (302 records) used a small
pysam-based `trim_fixture.py`: keep every record overlapping (+/-1000-5000bp,
per file) a `tests/data/demo_delly.vcf.gz` locus first, then fill the
remaining slots by taking evenly-spaced records from the rest of the file
(so the trim still spreads across chr21 rather than clustering at the
start), re-sort into original file order, write with
`pysam.VariantFile(..., 'wz')`, `pysam.tabix_index(preset='vcf')`.

`lumpy_raw_hg38_chr21_hg002.vcf.gz` is the one exception: it was bgzip/tabix'd
directly from the plain-text `lumpy_raw.vcf` via
`pysam.tabix_compress`/`pysam.tabix_index` *without* ever opening it through
`pysam.VariantFile` first, because doing so silently injects a `##contig`
line even when the source text has none — and the whole point of this
fixture is the genuine raw-lumpyexpress dialect of **zero** `##contig` lines
in the header text.

## Problems encountered (kept for provenance / re-running the pipeline)

1. **bcftools/tabix/bgzip are not on `PATH`** in this worktree/environment;
   used `/Users/burgshrimps/.local/share/mamba/envs/dicast-verify/bin/{bgzip,tabix}`
   plus plain-text (`grep`/`awk`) trimming instead of the `bcftools view | head`
   recipe. All record-count/stat verification used pysam 0.24 from that same
   env, not bcftools.
2. **smoove/svtyper version pin**: bioconda `smoove=0.2.8` defaults to
   `svtyper=0.1.4`, but smoove 0.2.8's genotyping step passes `--max_ci_dist`,
   a flag svtyper 0.1.4 doesn't recognize (`svtyper: error: unrecognized
   arguments: --max_ci_dist 0`, which panics smoove). Fixed with
   `micromamba install -y -n smoove -c bioconda -c conda-forge 'svtyper=0.7.0'`.
3. **Missing `@RG` on the shared caller BAM**: `~/dicast_callers/bam/caller.bam`
   has no `@RG` line (built via a textual `samtools view` reheader by a
   separate remote-setup step); svtyper's `Sample.from_bam()` does
   `bam.header['RG'][0]['SM']` and raises `KeyError: 'RG'`, crashing smoove.
   Rather than mutate the shared BAM (other caller runs may depend on its
   exact bytes), a separate `caller_rg.bam` copy was made via
   `samtools addreplacerg -r '@RG\tID:HG002\tSM:HG002\tLB:lib1\tPL:ILLUMINA'`
   and used for both smoove and lumpyexpress.
4. **Broken `lumpyexpress` wrapper**: bioconda `lumpy-sv=0.3.0-3` ships a
   `lumpyexpress.config` that points at `bin/scripts/bamkit/{bamgroupreads,
   bamfilterrg,bamlibs}.py` and `bin/scripts/pairend_distro.py`, none of
   which exist in the installed package (no `bamkit/` subdirectory at all;
   `pairend_distro.py` only exists under `share/lumpy-sv-0.3.0-3/scripts/`).
   Fixed by fetching the three `bamkit` scripts from
   `github.com/cc2qe/bamkit` (the actual upstream repo lumpy-sv's `bamkit/`
   submodule points to) and copying `pairend_distro.py` into
   `bin/scripts/`. Also printed two harmless shell errors
   (`line 15: -n: command not found`, `line 16: [: ==: unary operator
   expected`) from the same broken config under `micromamba run`; these did
   not affect the output VCF and were left as-is.
5. **`simple-event-annotation.R` fails on current Bioconductor**: the
   unmodified 2018 PapenfussLab script assigns
   `info(vcf[gr$sourceId])$SVLEN <- gr$svLen` without ever declaring `SVLEN`
   in the header or in `info(vcf)`; the `bioconductor-variantannotation`
   build installed here rejects that silently-relied-on behavior
   (`Error in .subassign_columns(x, nsbs, value): provided 68 variables to
   replace 67 variables`). Fixed with a 2-line addition mirroring the
   script's existing `SIMPLE_TYPE` init: an `SVLEN` header declaration
   (`Number=1, Type=Integer`) and `info(vcf)$SVLEN <- NA_integer_` before the
   classification loop. Ran cleanly afterwards: 912 records in, 912 out, 646
   with `SIMPLE_TYPE`/`SVLEN` set (the other 266 are single/unpaired
   breakends `breakpointRanges()` cannot classify).
6. **cnvnator2VCF.pl not shipped by the default bioconda build**: the
   solved build (`h9c7f56d_2`, python 3.9-linked) ships only `bin/cnvnator`;
   `cnvnator2VCF.pl` only exists in a newer build
   (`cnvnator=0.4.1=py313h3ef7bf5_12`) that conflicts with the env's
   python=3.9 pin and fails to solve in-place. Fixed by downloading that
   `.conda` package directly, extracting `bin/cnvnator2VCF.pl`, and copying
   it into the `cnvnator` env's `bin/` (its shebang is an unpatched
   conda-build placeholder, so it was invoked as `perl .../cnvnator2VCF.pl`
   with the system perl instead).
7. **gridss source files have no trailing newline**: `gridss.vcf` and
   `gridss-na12878.vcf` (both used verbatim for the public
   `gridss_raw_*` fixtures) have no trailing newline after their last data
   line, which makes `grep -c '^#'`/`grep -vc '^#'` undercount by 1 on
   macOS/BSD grep (7 vs. actual 8 records for `gridss.vcf`; 59 vs. actual 60
   for `gridss-na12878.vcf`). `grep -v '^#' file | wc -l` and pysam
   iteration were used for the final counts instead.
8. **`gridss.vcf`'s breakend records are not genome-sorted** (event pairs
   are interleaved, e.g. chr1, chr12, chr12, chr12, chr1, chr10, chr10,
   chr11), which made `tabix -p vcf` fail with `Chromosome blocks not
   continuous`. Fixed by sorting the 8 data lines by `(chrom, pos)` before
   bgzip+tabix, with the header left untouched (so this one file's on-disk
   record order is *not* byte-identical to the upstream source, unlike every
   other public download here).
9. **delly/cnvnator omit `INFO/SVLEN` from the header entirely**
   (`delly_hg38_trio`, `delly_grch37_hg002_del`, `cnvnator_grch37_hg002`,
   `cnvnator_hg38_chr21_hg002`): both callers encode SV length via
   `INFO/END` (+`INFO/INSLEN` for delly insertions) only. pysam's
   `rec.info.get('SVLEN')` raises `ValueError: Invalid header` on these
   files rather than returning `None`, because that method only tolerates a
   *declared* key that happens to be absent on one record — a key the
   header never declares at all is a hard error. `dicast/vcf_input.py`'s
   `_info_get()` guards every INFO lookup in this module against exactly

    `dicast/vcf_input.py` reads `rec.stop` unconditionally rather than
